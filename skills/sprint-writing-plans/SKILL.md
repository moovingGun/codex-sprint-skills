# Sprint Writing Plans

Modified adaptation, 2026-11-04. Source, revision, and changes: [ATTRIBUTION.md](ATTRIBUTION.md).

## 시작
README와 사용자가 제공한 운영 조건을 먼저 읽는다. 기존 코드가 있다면 구조와
실행 명령을 확인한다. 사용자 스택과 작업 방식을 유지한다.
이 Skill은 계획 작성과 추적을 지원하며 별도 승인 단계나 서브에이전트를 요구하지 않는다.
사용자가 구현까지 요청했다면 실행 가능한 계획을 만든 뒤 같은 세션에서 계속한다.

## 최소 산출물
기존 추적 문서가 없다면 REQUIREMENTS.md를 만든다.

| ID | 요구·원문 위치 | 수락 조건 | 구현 파일·심볼 | 검증 명령·테스트 | 상태·근거 |
|---|---|---|---|---|---|

- 필수 요구를 빠짐없이 추출한다. 명시 요구, 담당자 답변, 구현 가정을 구분한다.
- 제공되지 않은 규칙·스키마·회고 문항을 지어내지 않는다.
- 시작 시 모르는 구현 위치는 미정으로 두고, 구현 시 실제 경로로 갱신한다.
- 상태는 TODO / DOING / VERIFIED / BLOCKED로 구분한다.
  코드 작성만 끝난 항목은 VERIFIED로 표시하지 않는다.
- 같은 테스트가 여러 요구를 확인할 수 있지만, 요구별 관찰 가능한 결과를 적는다.

## 계획
사용자가 정한 제한 시간과 남은 시간을 기준으로 계획한다.
별도 배분이 없으면 필수 구현에 약 65%, 통합 검증에 20%, 제출·실행 문서에 15%를
초기 배분하되 실제 진척에 따라 조정한다. 필수 기능을 임의로 삭제하지 않는다.

각 작업에는 다음만 적는다.
1. 연결되는 요구 ID와 완료 시 관찰 가능한 동작.
2. 책임을 가진 파일, 입력·출력 계약, 필요한 의존 작업.
3. 검증할 실패 사례와 실행 명령.

계획에 구현 전체를 미리 작성하지 않는다. 가장 작은 수직 기능부터 연결한다.
입력 검증·저장·오류 처리·권한·출력 계약을 UI 이후로 전부 미루지 않는다.
워커·큐·추가 DB는 요구와 실행 시간에 근거가 있을 때만 선택한다.

## 확인과 추적
- 채점 계약, 권한, 데이터 보존, 목적함수에 영향을 주는 모호함은 담당자 질문으로
  정리한다. 답변에 의존하지 않는 작업은 계속한다.
- 기능별로 요구 ID → 구현 → 테스트 → 실제 결과를 연결한다.
- 중요한 선택은 DECISIONS.md에 문제·대안·선택·이유·부작용·증거를 짧게 기록한다.
- AI 제안을 채택·수정·폐기한 경우 실제 근거만 기록한다.
- 단계가 끝나면 README를 다시 읽고 작업이 없는 요구와 근거가 없는 완료를 찾는다.
- 막힌 항목과 미완료를 숨기지 않고 다음 작업과 함께 보고한다.

## 범위
범용 개발 지침이다. 과제 원문·실데이터·비공개 대화·완성 앱을 포함하지 않는다.
실행 스크립트·외부 서비스·다른 Skill 의존성이 없다.
