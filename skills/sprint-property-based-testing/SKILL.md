# Sprint Property-Based Testing (LITE)

Modified adaptation, 2026-11-04. Source, revision, and changes: [ATTRIBUTION.md](ATTRIBUTION.md).
Adapted from Trail of Bits contributors; this adaptation is CC-BY-SA-4.0.
랜덤 생성·완전탐색·변이 캠페인을 기본 작업에 넣지 않는다.
계산 기능을 만들 때 독립 검증기를 함께 만든다. 완성된 검증기부터 만들며 구현을 지연하지 않는다.

## 최소 독립 검증기
- README의 필수 제약을 기준으로 원입력 + 최종 출력 → 위반 목록을 반환한다.
- 플래너의 제약 판정 함수를 재사용하지 않는다. 파서와 자료형은 공유할 수 있다.
- 과제별 필수 제약과 1:1로 연결한다. 예: 참조 ID, 누락·중복, 정원, 시각과 구간 시간.
- 실제 성공 결과를 검증하고 통과한 결과만 성공 상태로 저장·공개한다.
  로그·실패 원인은 저장할 수 있다. 검증 실패로 기존 성공 결과를 덮어쓰지 않는다.
- 결과에 계산에 사용한 입력 버전을 연결한다. 공개 시 현재 버전과 일치하는지 확인해
  계산 중 데이터 교체로 과거 결과가 현재 결과처럼 공개되지 않게 한다.

## 확인은 작은 사례로
1. 손으로 확인 가능한 정상 결과 하나를 수락하는지 확인한다.
2. 그 결과의 서로 다른 필수 제약 2종을 하나씩 깨뜨려 정확한 이유로 거부되는지 확인한다.
   무관한 파싱 오류로 실패하면 해당 제약의 검증 증거가 아니다.
3. 실제 export API의 JSON이 README 스키마와 맞는지는 핵심 흐름 테스트에 합친다.
기존 테스트가 이 내용을 확인하면 재사용한다. 같은 fixture와 검사를 다시 만들지 않는다.
변경한 제약·파서·출력 형태에 영향을 받는 사례만 다시 실행한다.

## 해 품질: 비용이 작을 때만
필수 목적함수와 미배정·위반 수 등 결과 지표는 명시한다.
짧게 증명 가능한 하한이 있으면 가정과 함께 사용한다. 그룹별 하한을 합하려면
그룹 사이 자원 공유가 불가능하다는 조건이 필요하다. 유효한 하한이 없으면
단순 기준선과 비교하거나 해 품질 미확인으로 남긴다. 하한 탐색 때문에 구현을 늦추지 않는다.
실행 가능성과 최적성을 구분한다. 같은 입력·제약·목적지표에 대한 유효한 하한과
실행 가능한 결과가 같을 때만 해당 최소화 지표에서 최적이라고 말한다.
0으로 나누거나 다른 지표의 하한으로 최적성을 주장하지 않는다.

검증기 위치·검사 항목·작은 사례 결과만 짧게 기록한다.
실행 스크립트·필수 외부 서비스·다른 Skill 의존성이 없다.
