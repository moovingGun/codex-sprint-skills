# Sprint Test-Driven Development

Modified adaptation, 2026-11-04. Source, revision, and changes: [ATTRIBUTION.md](ATTRIBUTION.md).

## 우선순위
README의 필수 계약과 실패 시 영향이 큰 동작부터 테스트한다.
기존 테스트 도구를 사용한다. 단순 변경에 새 프레임워크를 도입하지 않는다.
테스트를 쉽게 만들려고 실제 요구나 실패 조건을 완화하지 않는다.

## Red → Green → Refactor
1. 구현 전에 외부에서 관찰 가능한 동작 하나를 테스트한다.
2. 실행해 의도한 assertion이 실패하는지 확인한다. 잘못된 import, 문법 오류,
   미설치 도구나 연결 실패는 원하는 Red의 증거가 아니다.
3. 계약을 만족하는 최소 구현을 작성한다. 예제 값만 반환하는 하드코딩은 피한다.
4. 대상 테스트와 관련 통합 테스트를 실행한다.
5. Green 상태에서 중복·이름·책임을 정리하고 다시 확인한다.

최종 완료 전에는 프로젝트의 필수 검사와 전체 테스트를 한 번 실행한다.
변경이 없고 새로운 의심도 없으면 같은 전체 검사를 반복하지 않는다.
실행할 수 없는 검사는 통과로 표시하지 않고 이유를 남긴다.

## 경계별 핵심 테스트
- 입력: 빈 파일, 필수 열 누락, 잘못된 타입, 중복키, 존재하지 않는 참조 ID.
- 적용: 전체 검증 후 원자적으로 반영되며 실패하면 기존 활성 데이터와 결과 유지.
- 버전: 이전 입력의 결과가 새로운 입력의 결과로 표시되지 않음.
- 실행: 중복 요청, 계산 오류, 재실행, 재시작의 실제 계약.
- 권한: UI를 거치지 않는 비로그인·다른 역할의 API 호출 거부.
- 출력: 정확한 필수 키·타입·범위·참조와 오류 시 응답 계약.
과제에 적용되는 항목을 고르고, 해당하지 않으면 이유를 기록한다.

## 테스트가 진짜인지 확인
테스트를 쓰기 전에 어떤 운영 코드 결함을 잡을지 한 문장으로 적는다.
실제 결과·저장 상태·응답을 확인하며 mock 호출만으로 성공을 판정하지 않는다.
시간·난수·외부 I/O만 필요한 범위에서 고정하고, 핵심 규칙을 mock으로 지우지 않는다.
음성 테스트는 잘못된 입력/출력이 거부되는지 확인한다.
변이 테스트는 실제 판정이나 상태 변경을 잠시 깨뜨렸을 때 테스트가 실패하는지
확인한다. 수행했다면 별도 임시 복사본이나 되돌릴 수 있는 격리 변경을 사용하고
복원 후 재검증한다. 사용자의 기존 작업을 덮어쓰지 않는다.

## 기존 구현과 리팩터링
이미 구현이 있다면 일괄 삭제하지 않는다. 현재 동작을 확인하고 핵심 계약·버그
재현 테스트를 추가한다. 이 경우 테스트 이후 작성 사실을 그대로 기록한다.
버그 수정은 실패 재현 → 최소 수정 → 통과·회귀 확인으로 진행한다.
설정·문서·UI 스타일에 의미 없는 단위 테스트를 추가하지 않는다.
새 테스트가 없는 변경은 대신 사용한 적절한 확인 방법을 남긴다.

## 증거
요구 ID, 테스트 이름, 명령, 결과를 기록한다.
실패를 일으키지 못한 테스트와 검증하지 못한 경로를 통과로 보고하지 않는다.
실행 스크립트·외부 서비스·다른 Skill 의존성이 없다.
