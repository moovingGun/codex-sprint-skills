# Sprint Test-Driven Development (LITE)

Modified adaptation, 2026-11-04. Source, revision, and changes: [ATTRIBUTION.md](ATTRIBUTION.md).
검증은 필수 서비스 완성을 지원한다. 테스트 개수나 커버리지 목표를 만들지 않는다.
검증기·테스트만 만드는 별도 선행 단계를 두지 않고 관련 기능과 함께 진행한다.

## 최소 확인 범주
과제에 해당하는 아래 범주를 작은 fixture와 API 테스트로 묶어 확인한다.
하나의 통합 테스트가 여러 요구를 확인해도 된다. 과제가 추가 검사를 요구하면 따른다.
1. 정상 핵심 흐름: 입력 적용 → 계산 → 독립 검증 → 조회 → 실제 export API 응답의
   정확한 필수 키·타입·참조 확인. 출력 파손 2종이 해당 이유로 거부되는지도 확인한다.
2. 입력 거부·보존: 잘못된 스키마와 없는 참조 ID를 각각 거부하고 기존 데이터·결과·
   버전이 유지되는지 확인한다. 해당 실패를 하나의 파라미터 테스트로 묶어도 된다.
3. 버전·실행 상태: 새 입력 적용 후 이전 결과가 현재 결과로 표시되지 않는지,
   실행 도중 입력이 바뀌면 이전 버전 결과가 현재 결과로 공개되지 않는지 확인한다.
   중복 실행과 계산 오류는 짧은 사례로 DB 상태 또는 API 응답을 확인한다.
4. 권한: 비로그인·다른 역할의 API 직접 호출을 거부한다.
   상태 코드는 README 계약을 따르고, 별도 계약이 없으면 보통 401/403을 사용한다.

빈 입력과 오류의 차이는 위 흐름의 짧은 추가 사례로 확인한다.
범주가 과제와 무관하면 이유를 적고 제외한다. 같은 검사를 다른 Skill에서 다시 작성하지 않는다.

## 테스트 작성
- 데이터 보존·권한·출력 계약과 버그 수정은 가능한 한 작은 실패 테스트부터 작성한다.
- 최소 import/실행 골격이 없으면 먼저 만든다. import 오류나 미설치는 의도한 Red가 아니다.
- 기대값은 요구 또는 손계산에서 정한다. 현재 출력을 정답으로 복사하지 않는다.
- 핵심 규칙을 mock으로 지우지 않는다. assertion을 약하게 바꾸지 않는다.
- 기존 코드를 일괄 삭제하지 않는다. UI 스타일·문서에 의미 없는 테스트를 만들지 않는다.
- 랜덤 생성·완전탐색·변이 캠페인·커버리지 목표는 기본 범위에서 제외한다.

## 재실행 규칙
- 처음 확인: 방금 구현한 요구의 대상 테스트만 실행한다.
- 수정 후: 실패 재현 테스트와 변경 영향이 있는 테스트만 다시 실행한다.
- 공용 파서·스키마·DB·권한·직렬화 변경: 연결된 핵심 테스트 묶음을 실행한다.
- 통과 이후 관련 변경이 없으면 재실행하지 않는다. 단순 문서 수정으로 앱 검사를 다시 하지 않는다.
- 제출 전에는 핵심 통합 묶음을 한 번 확인한다. 빠른 기존 전체 검사가 이를 포함하면
  그 명령 하나로 대체하고 중복 실행하지 않는다. 긴 전체 검사를 새로 강제하지 않는다.
긴 검사는 시간을 제한해 중단하고 미실행 범위를 기록한다. 실패·시간 초과는 통과가 아니다.
검증에 시간을 써야 한다면 채점·실행 가능성·데이터 보존에 직접 영향을 주는 것부터 한다.

실행 스크립트·외부 서비스·다른 Skill 의존성이 없다.
